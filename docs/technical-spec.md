This document describes how the DUX Vault codebase is implemented today. The business rules still live in [docs/app-spec.md](docs/app-spec.md); this file explains the stack, folder layout, runtime flow, and the conventions to follow when extending the project.

## 1. Design Goals

The project is intentionally small: one React frontend, one FastAPI backend, and a limited set of read-only document search flows. The guiding rule is to keep the code simple enough that a data-oriented maintainer and a newer developer can safely extend it without learning a large framework stack.

That means:

- Prefer plain React, FastAPI, and SQLAlchemy over heavier abstractions.
- Keep page-specific configuration close to the page that uses it.
- Put reusable stateless helpers in a shared utilities module.
- Keep all business rules aligned with the App Spec and the database schema exactly as implemented.

## 5. Frontend Implementation

### 5.1 Routing and layout

The frontend route tree is defined in [frontend/src/router.tsx](frontend/src/router.tsx). The app has these visible states:

- login screen
- unauthorized screen
- app shell with the top menu bar
- six document search pages
- not found screen

The persistent layout lives in [frontend/src/layouts/AppShell.tsx](frontend/src/layouts/AppShell.tsx). The top nav is rendered by [frontend/src/components/MenuBar.tsx](frontend/src/components/MenuBar.tsx).

The menu bar renders as two stacked rows:

- an identity bar on `bg-b2b-dark` holding the logo mark, the application name, the signed-in user's initials and display name, and the logout action
- a persistent horizontal tab row underneath, one tab per document option

The tab row is [frontend/src/components/NavTabs.tsx](frontend/src/components/NavTabs.tsx), driven entirely by `navigationItems` in [frontend/src/config/navigation.ts](frontend/src/config/navigation.ts). Each `NavigationItem` carries a `tabLabel` for the short tab text alongside the longer `label`.

This matches the persistent menu bar described in the App Spec, which specifies a bar across the top of every screen exposing the options the signed-in user is entitled to.

### 5.2 Search pages

Each document option has a small page component in [frontend/src/pages](frontend/src/pages) that only provides:

- the option key
- the title
- a short description
- the search fields
- the result columns

The shared shell is [frontend/src/pages/SearchPageTemplate.tsx](frontend/src/pages/SearchPageTemplate.tsx). It owns:

- form state
- query execution via TanStack Query
- result caching for the last submitted filter set
- document viewer state
- the result count line shown above the grid
- the "download only" footnote shown when any result cannot be rendered inline
- a single `downloadRow` callback shared by the grid rows and the viewer header

The page title and description render inside the search card itself; there is no separate header card above it.

A `SearchField` may name an `exclusiveWith` partner. `SearchForm` disables a field while its
partner holds a value, which is how the date/number pairs on options 2 and 4 to 6 are kept
mutually exclusive without an error state. Declare it on both members of the pair.

The shared UI pieces are:

- [frontend/src/components/SearchForm.tsx](frontend/src/components/SearchForm.tsx)
- [frontend/src/components/ResultsGrid.tsx](frontend/src/components/ResultsGrid.tsx)
- [frontend/src/components/DocumentViewer.tsx](frontend/src/components/DocumentViewer.tsx)
- the presentational primitives in `frontend/src/components/ui` described in section 5.5

`DocumentViewer` behavior worth knowing before changing it:

- it accepts an optional `onDownload`; when supplied, a Download button appears in the modal header
- `Escape` closes the overlay, as does the header close button
- for PDFs it renders every page in one scrollable column and reports the page count beneath the body
- for spreadsheets it still parses with `xlsx` and exposes one tab per sheet

### 5.3 Result grid behavior

The grid is intentionally generic because every search returns a different column set. The backend returns raw row objects, and the page decides which columns to show.

Important UX rule already implemented:

- `RESOURCECONTENT` can be long, so the grid contains it in a bounded scrollable cell instead of letting it stretch the table.
- Rows render `View` and `Download` actions where supported.
- The actions column is right-aligned. `View` uses the `outline` button variant and `Download` the `primary` variant, both with a leading icon.
- A row whose file type cannot be rendered inline drops the `View` action and shows a short note in its place.

### 5.4 API layer

Frontend API code is split by concern:

- [frontend/src/api/client.ts](frontend/src/api/client.ts) builds backend URLs, defaulting to the
  page's own origin in a production build and to `http://localhost:8000` under the dev server;
  `VITE_BACKEND_URL` overrides both. It sends `credentials: "include"` by default
- [frontend/src/api/auth.ts](frontend/src/api/auth.ts) handles login/logout/session requests
- [frontend/src/api/documents.ts](frontend/src/api/documents.ts) handles search and document view/download URLs

TanStack Query is used for search results and user session state. There is no Redux store.

### 5.5 Styling system and UI primitives

Styling is Tailwind v4 with a small set of project tokens declared in the `@theme` block of [frontend/src/styles.css](frontend/src/styles.css):

| Token                  | Value                             | Used as                                    |
| ---------------------- | --------------------------------- | ------------------------------------------ |
| `--font-sans`          | Open Sans                         | default body font                          |
| `--font-display`       | Poppins                           | `font-display` for headings and controls   |
| `--color-b2b-red`      | `#ed2e24`                         | `bg-b2b-red`, `text-b2b-red`, `border-b2b-red` |
| `--color-b2b-red-soft` | `#f8dddb`                         | `bg-b2b-red-soft` for hover and active fills |
| `--color-b2b-dark`     | `#3a3a3a`                         | `bg-b2b-dark` for the identity bar         |
| `--shadow-b2b`         | `3px 5px 5px rgba(32,29,29,0.25)` | `shadow-b2b` on raised surfaces            |

Two presentational primitives live in `frontend/src/components/ui`:

- [frontend/src/components/ui/Button.tsx](frontend/src/components/ui/Button.tsx) — variants `primary`, `outline`, `subtle`, `ghost`; sizes `sm`, `md`, `icon`; optional leading `icon` node. Extends the native button props, so `type`, `disabled` and `aria-*` pass straight through.
- [frontend/src/components/ui/Card.tsx](frontend/src/components/ui/Card.tsx) — the standard raised white surface, with `padding` of `none`, `sm`, or `md`.

Icons are hand-written inline SVG components in [frontend/src/components/icons/index.tsx](frontend/src/components/icons/index.tsx). They size from `className` and take their colour from `currentColor`. This is deliberate: there is no icon package in `package.json` and adding one is not necessary for the handful of glyphs this app uses.

The convention when adding UI:

- use a primitive, or add a variant to one, rather than repeating its Tailwind class string
- reach for the tokens above instead of hard-coding the brand red or the shadow

One known gap: the neutral greys are still literal hex values scattered through the components — `#414041` body text, `#666666` muted text, `#888888` subtle text, `#ebebeb` borders, `#f1f1f1` page background, `#f2f2f2` fills. They are consistent in practice but are not yet tokens, and promoting them would be a reasonable future cleanup.

## 6. Backend Implementation

### 6.1 App startup

The FastAPI app is created in [backend/app/main.py](backend/app/main.py).

It currently:

- configures logging
- validates the configuration before serving (below)
- adds session middleware
- adds CORS for the frontend origins
- mounts the API routers under `/api`
- serves built frontend assets if `backend/static` exists
- returns a JSON 404 for unknown `/api/*` paths

`Settings.validate_for_runtime` runs at import. It raises when `APP_ENV` is production and any of
`AUTH_BYPASS_ENABLED`, a placeholder `SESSION_SECRET`, or `SESSION_COOKIE_SECURE=false` would
leave the app unauthenticated or its cookie in clear; outside production it logs each as a
warning instead, so local development still works. This exists because `env_file` is hardcoded to
`.env.development` and `APP_ENV` otherwise only selects the log format — nothing else connects the
environment to those settings, so without the check a deployment that forgets one starts up
looking healthy while being wide open.

### 6.1.1 API envelope and error handling

All JSON endpoints return a consistent envelope:

- success: `{ "success": true, "data": ..., "error": null }`
- error: `{ "success": false, "data": null, "error": { "code": "...", "message": "...", "details": ... } }`

This keeps the frontend parsing simple and makes failures predictable for the team. FastAPI exception handlers in [backend/app/main.py](backend/app/main.py) convert handled errors into the same structure, and the frontend client unwraps the `data` payload automatically.

The file/document path resolver is also guarded at the service boundary so a malformed document root mismatch becomes a controlled API error instead of an uncaught exception.

### 6.2 Auth flow

The backend owns authentication.

Current behavior:

- `POST /api/auth/login` takes `{username, password}`, binds against a domain controller over LDAPS, resolves group membership, and stores the resulting identity in the session
- `POST /api/auth/logout` clears the session and returns 204
- `GET /api/auth/me` returns the current user from the session

The username may be given as `CORP\\jsmith`, `jsmith@corp.local`, or `jsmith`.

Group membership is read over the signing-in user's own connection first, which is all most
directories need — Active Directory lets an authenticated user read membership by default. An
empty result is ambiguous, meaning either that the user is in no groups or that the directory
will not let them look, and those are indistinguishable from the application's side. So when
`LDAP_BIND_DN` is configured, an empty result is retried through the service account.

Falling back rather than choosing matters on both sides: a user whose own read is refused is
covered without routing every sign-in through one account, and a broken service-account
password degrades only the users who actually need it instead of turning every sign-in into a
500.

Membership is resolved recursively with `LDAP_MATCHING_RULE_IN_CHAIN`, so nested
groups count. Matched Active Directory groups are reduced to the entitlement tokens
`general` and `confidential` before being stored in the session or sent to the browser -
a user can belong to more AD groups than fit in a signed cookie, and the browser has no
need for the directory's group names. Entitlements are resolved at sign-in and cached for
the session lifetime, so a group change takes effect at the user's next sign-in.

Repeated failed sign-ins are throttled per username and per client address
(`LOGIN_MAX_ATTEMPTS` within `LOGIN_ATTEMPT_WINDOW_SECONDS`) so that attempts through this
application cannot lock a domain account.

Auth-related implementation lives in:

- [backend/app/api/routes/auth.py](backend/app/api/routes/auth.py)
- [backend/app/auth/dependencies.py](backend/app/auth/dependencies.py)
- [backend/app/auth/ldap_client.py](backend/app/auth/ldap_client.py)

Two scripts diagnose this path without starting the app. Both need a real terminal, because
the password is read with `getpass`:

- [backend/scripts/fetch_ca_cert.py](backend/scripts/fetch_ca_cert.py) builds the CA bundle from the directory
- [backend/scripts/check_ad_login.py](backend/scripts/check_ad_login.py) reports what the app would see for one account: whether the bind succeeds, whether group membership can be read, whether the configured entitlement groups exist under the name the app compares, and the resulting entitlements. `--for` binds as one account and reads another's membership, which is the only way to test the service-account fallback

**`AUTH_BYPASS_ENABLED` is not a login shortcut.** When it is on, `get_current_user` returns a
fully-entitled stand-in user **with no session cookie at all**, and `_require` returns early, so
every endpoint is open to anyone who can reach the host — Confidential documents included. With
`AUTH_BYPASS_GROUPS` empty the stand-in holds both entitlements. It exists so document flows can
be exercised when the directory is unreachable, and nothing else. `Settings.validate_for_runtime`
refuses to start with it on when `APP_ENV` is production, and logs a warning otherwise.

### 6.3 Group checks

Group gating is enforced server-side in the dependency layer.

- General group users can access options 1, 2, 3, 5, and 6.
- Confidential group users can access all six options.
- The backend checks group membership on every request that needs it.

For view and download there is a second check, because the entitlement check alone tests the
*option named in the URL*, and that option is chosen by the caller. `get_document_path` resolves
a path from a `RESOURCEID` alone, so without tying the document to the option, a user entitled to
a General option could request `/api/documents/supplier-invoices/general/<confidential id>/view`
and be served a Confidential document. Every option draws from exactly one IDM view, so
`document_belongs_to_option` (`OPTION_TABLE_MAP` in
[backend/app/db/document_repository.py](backend/app/db/document_repository.py)) confirms
membership before the path is resolved. A mismatch returns 404, not 403 — whether the id exists
under a different option is not the caller's business.

Both handlers share `_authorise_document` in
[backend/app/api/routes/documents.py](backend/app/api/routes/documents.py) so the checks cannot
drift apart between view and download. Confidential access is logged there (user, resource id,
action) as required by app-spec Section 7, after access is granted and before the path is
resolved, so a document missing from disk still leaves a record that it was released.

### 6.4 Database access

SQL Server access is implemented with two SQLAlchemy engines in [backend/app/db/session.py](backend/app/db/session.py):

- `idm_engine` for the IDM metadata database
- `docmgmt_engine` for the document index database

The current connection string uses ODBC Driver 18 and explicit TLS settings. Development can trust a self-signed SQL Server certificate via `DB_TRUST_SERVER_CERTIFICATE=true`.

### 6.5 Query layout

Each search option has its own SQL file in [backend/app/db/queries](backend/app/db/queries):

- `ar_registrations.py`
- `ar_remittances.py`
- `supplier_master_forms.py`
- `supplier_invoices.py`

The query repository in [backend/app/db/document_repository.py](backend/app/db/document_repository.py) maps an option key to the right SQL and returns raw dictionaries. The backend does not reshape the rows into a custom response object because the frontend is already built to render the actual query columns.

### 6.6 File resolution and streaming

The document path flow is split into two pieces:

- [backend/app/utils/path_utils.py](backend/app/utils/path_utils.py) contains the pure path translation helper
- [backend/app/services/file_server.py](backend/app/services/file_server.py) resolves the local path, checks file existence, chooses the content type, and returns a `FileResponse`

This separation is deliberate:

- pure helpers are easy to test
- I/O stays in services
- the search/query layer stays separate from file streaming

### 6.7 Additional utility helpers

Pure validation helpers live in [backend/app/utils/document_utils.py](backend/app/utils/document_utils.py). At present that module handles:

- ISO date validation for both the remittance creation filter and the invoice M3 date filter.
  Both date pickers submit `yyyy-mm-dd`; the `ddmmyy` form is no longer accepted from callers,
  though the stored `M3_Date` column is still ddmmyy and is still converted in SQL.
- rejection of mutually exclusive filter pairs (`reject_combined_filters`), used by options 2
  and 4 to 6 for their date/number pair — see App Spec section 5.8
- file type inference for downloads and inline viewing

## 7. Document Flow

The implemented end-to-end flow is:

1. User signs in through the backend session flow.
2. The frontend loads the current user from `/api/auth/me`.
3. The user opens one of the six search pages.
4. The page submits the relevant filters to the backend.
5. The backend runs the option-specific SQL against the IDM metadata database.
6. Search results are shown in the grid.
7. `View` opens the document viewer when the file type supports inline rendering. The viewer offers its own `Download` action, and closing it returns to the results list with the search and its results intact.
8. `Download` opens the browser download flow using the original `RESOURCENAME`.
9. The backend resolves `RESOURCEID` through `DUX_DocMgmt.dbo.Document` and then translates the canonical document root to the environment-local path.

The important implementation detail is that the frontend does not build document paths itself. It only passes the `RESOURCEID` and `RESOURCENAME` back to the backend.

## 8. Current UX Conventions

The UI has already been simplified in a few places to keep it maintainable for a small team:

- the top nav is an identity bar plus a persistent tab row, so every option the user is entitled to is reachable in one click from anywhere
- page headers use short descriptions instead of internal implementation notes
- search pages share one template so each option stays small
- the results grid contains long `RESOURCECONTENT` values instead of letting them expand the page width
- shared UI is assembled from the `components/ui` primitives rather than repeated Tailwind class strings
- icons are inline SVG components rather than a third-party icon package
- the search card is width-constrained (`max-w-xl`) while the results area is wider (`max-w-5xl`), so forms stay readable and tables get room

If future work adds new UI, keep those conventions intact rather than reintroducing wide, repetitive layouts.

## 10. Where To Put New Code

Use these placements consistently:

- request handlers: `backend/app/api/routes`
- session and group logic: `backend/app/auth`
- SQL and repository logic: `backend/app/db`
- pure helper functions: `backend/app/utils`
- file/path I/O: `backend/app/services`
- shared response models: `backend/app/schemas`
- React page shells and page-specific config: `frontend/src/pages`

- inline SVG icons: `frontend/src/components/icons`

- shared frontend types: `frontend/src/types`

If a function has no side effects and can be tested without touching the network, database, or filesystem, it probably belongs in `app/utils` rather than living next to a route.

## 11. Serving the App

The backend serves the built SPA itself, so the app runs on a single origin. That is the
deployment shape to prefer, and not only for tidiness: same-origin removes CORS entirely, keeps
the session cookie same-site so `SameSite=Lax` stays valid, makes deep-link refreshes work
through the SPA fallback, and means the PDF and XLSX viewers inherit the session without
needing credentialed cross-origin requests.

```bash
cd backend
make build-frontend   # builds the SPA into backend/static/
make tls-cert         # once; self-signed, SAN includes the LAN address
make serve            # https on 0.0.0.0:8000
```

`make build-frontend` builds with **no** `VITE_BACKEND_URL`, so `client.ts` falls back to
same-origin and emits relative `/api/...` paths. That fallback is environment-aware: the dev
server defaults to `http://localhost:8000` because Vite runs on a different port, while a
production build defaults to empty. Setting `VITE_BACKEND_URL` overrides either, for a
deployment that does split the two across hosts — in which case `FRONTEND_ORIGINS` must list the
frontend origin exactly, `SESSION_COOKIE_SAMESITE` must become `none` with
`SESSION_COOKIE_SECURE=true`, and the two `DocumentViewer` fetches need `withCredentials`.

Because the URL is baked in at build time, a stale `backend/static/` serves yesterday's
frontend: re-run `make build-frontend` after any frontend change. The target greps the output
bundle for an absolute backend URL and warns if one survived.

TLS is part of the minimum rather than a refinement, because users type real Active Directory
passwords into this app and a simple bind sends them onward to the DC — plain http would put
both the password and the session cookie on the wire in clear. The certificate is self-signed,
so browsers warn once per user; an internal-CA certificate would avoid that at the cost of a
request to IT.

`make dev` stays plain http and therefore sets `SESSION_COOKIE_SECURE=false` for its own
process only. Browsers refuse to store a `Secure` cookie over http from anything but
`localhost`, so without that override signing in over a LAN address would appear to succeed and
then drop the session on the next request. Note also that `--reload` watches `.py` files and not
`.env`, so a configuration change needs a manual restart.

### Container

`docker/backend.Dockerfile` copies only `backend/app` and `backend/scripts`, so it currently
builds an API-only image: no frontend, and no CA bundle. Deploying from it needs a frontend build
stage (or an nginx tier), the CA bundle either baked in or mounted, TLS termination, and a
non-development environment file — `docker/docker-compose.yml` passes `.env.development`
straight through.
